## ปัญหา

พอคุณเปิด Claude Code หลายหน้าต่างพร้อมกันบนโปรเจกต์เดียว จะเจอ 4 อย่างนี้เสมอ:

| | อาการ |
|---|---|
| 1 | **เขียนทับกัน** — สอง session แก้ไฟล์เดียวกัน คนที่ merge ทีหลังชนะเงียบๆ |
| 2 | **งานหาย** — session จบแล้วแต่ยังไม่ push ไม่มีใครรู้จนกว่าจะไปไล่หา |
| 3 | **กติกาจาง** — session ที่ถูกเปิดต่อๆ กันมา ไม่รู้กฎที่ session แรกเพิ่งเรียนรู้ |
| 4 | **ตัวเลขที่เชื่อไม่ได้** — แต่ละ session วัดคนละวิธี แล้วเอาผลมารวมกัน |

> 🔑 **ข้อ 4 แพงที่สุด และเป็นข้อที่แทบไม่มีใครแก้**
> เพราะ 3 ข้อแรกพังแล้วเห็นทันที · **ข้อ 4 พังแล้วดูเหมือนทำงานได้ปกติ**

## LANES คืออะไร

**ห้าเสาที่ต้องมีครบ ถึงจะทำงานขนานได้จริง**

| | | คืออะไร |
|---|---|---|
| **L** | **Lanes** | เขตไฟล์ต่อแผนก — **ด่านใน CI บล็อกจริง ไม่ใช่ข้อตกลง** |
| **A** | **Auto-merge** | commit ขึ้นต้น `done(...)` → ตรวจ 5 ด่าน → merge เอง |
| **N** | **Notes** | บทเรียน + การตัดสินใจ **อยู่ในไฟล์ ไม่ใช่ในบทสนทนา** |
| **E** | **Evidence** | ห้ามเชื่อสิ่งที่ยังไม่ได้วัด · **ด่านต้องพิสูจน์ว่าแดงได้จริง** |
| **S** | **Scope** | ส่งต่อเมื่องานถัดไป *ไม่ต้องรู้ผล* ของงานนี้ · เพดาน session พร้อมกัน 3–5 |

> **L กับ A ทำให้ทำงานขนานได้**
> **N กับ E ทำให้ผลลัพธ์เชื่อถือได้**
> **S ทำให้มันคุ้ม**
>
> **ทีมส่วนใหญ่ทำแค่ L กับ A แล้วสงสัยว่าทำไมยิ่งขนานยิ่งพลาด**

## ในทางปฏิบัติมันทำงานยังไง

### เขตไฟล์ (`docs/team/ownership.json`)

```json
{
  "coordinatorLocked": ["src/lib/", "src/config/"],
  "domains": {
    "frontend": ["src/components/frontend/"],
    "api":      ["src/api/"]
  }
}
```

**session ของแผนก `frontend` แตะ `src/lib/` = CI ตีกลับ**

🔑 **แบ่งตาม "ใครเป็นเจ้าของการตัดสินใจ" ไม่ใช่ตามชนิดไฟล์**

### วงจรของแต่ละ session

```
1. อ่าน CLAUDE.md + เขตของตัวเอง            ← โหลดอัตโนมัติ
2. เช็คว่ามีใครทำเขตเดียวกันอยู่ไหม
3. branch: parallel/<แผนก>-<งาน>            ← push ทันที = ประกาศว่ากำลังทำ
4. ทำงาน + เขียนเทสต์
5. commit สุดท้าย: done(<แผนก>-<งาน>):     ← ตัวจุด auto-merge
6. push แล้วยืนยันว่าถึงจริง
```

### 3 คำสั่งที่ต้องได้ผลว่าง ก่อนบอกว่า "ส่งแล้ว"

```bash
git status --porcelain               # ต้องว่าง
git log --oneline @{u}..HEAD         # ต้องว่าง = ถึง remote จริง
git log --oneline origin/main..HEAD  # ต้องอยู่บน parallel/ และ push แล้ว
```

> **`git commit` ผ่าน ≠ ของถึงมือคนอื่น**

## บทเรียนที่จ่ายราคาไปแล้ว

ระบบนี้ไม่ได้ออกแบบบนกระดาษ — **ทุกกฎมาจากของที่พังจริง** ตัวอย่าง:

**🔴 ผลบวกลวงจากเครื่องมือวัด — ราคา: work order ทั้งใบ**
มีคนรายงานว่า *"ปิดกล่องแล้วทั้งหน้าค้าง ทำซ้ำได้ 100%"* → เปิดงานให้คนไปแก้ → **ไปวัดจริงแล้วไม่มีบั๊กนี้เลย**
สาเหตุ: เบราว์เซอร์ที่ใช้ตรวจถูกซ่อนอยู่ ⇒ หยุดเล่นแอนิเมชัน ⇒ **อาการเหมือนบั๊กจริงเป๊ะ**
⇒ **สิ่งที่ปิดประเด็นได้คือ "เคสควบคุม"** — เอาเคสที่เกิดบั๊กนี้ไม่ได้โดยนิยาม ไปวัดในสภาพเดียวกัน

**🔴 ความล้มลูกโซ่ทำให้ 1 บั๊กดูเหมือน 4**
สคริปต์ทดสอบรายงาน *"7 ผ่าน / 4 ล้ม"* — ที่จริงข้อแรกพัง แล้วอีก 3 ล้มตามเพราะไม่มีข้อมูลให้ทำงานด้วย
⇒ **ถ้าไม่ตรวจซ้ำ จะไปแก้ของที่ไม่ได้พังเลย**

**🔴 กติกาบวมจนย้อนมาทำร้ายตัวเอง**
ไฟล์กติกาโต **6.3 เท่าใน 8 วัน** ⇒ ทุก session ต้องอ่าน **~17,500 tokens ก่อนเริ่มงาน**
> **เราเขียนกฎเพิ่มทุกครั้งที่พลาด เพื่อไม่ให้พลาดซ้ำ — แต่ยิ่งเขียน โอกาสที่กฎข้อใดข้อหนึ่งถูกมองข้ามก็ยิ่งสูง**
⇒ แยกเป็นชั้น + **ด่านคุมขนาด** ⇒ ลดลง 58% โดยไม่ตัดบทเรียนทิ้งสักข้อ

**🧨 อ้างเลขที่ถูก rollback**
ทดสอบด้วยธุรกรรมที่ยกเลิกทิ้ง → สะอาดมาก **แต่เลขที่ระบบออกให้ถูกคืนเข้ากอง แล้วข้อมูลจริงใบถัดไปหยิบไปใช้**
⇒ รายงานที่เขียนว่า *"บิลทดสอบเลขที่ X"* **ชี้ไปที่ข้อมูลลูกค้าจริงในอีก 30 นาที**

📖 **อ่านครบทั้งชุด:** [`reference/failure-modes.md`](reference/failure-modes.md) · [`reference/lanes-concept.md`](reference/lanes-concept.md)

## สิ่งที่ทำให้ LANES ต่างจากคู่มือทั่วไป

คู่มือ multi-agent ส่วนใหญ่หยุดที่ *"แบ่งไฟล์กันแล้วใช้ worktree"*

**LANES เพิ่ม 2 อย่างที่มาจากการเจ็บจริง:**

**① ด่านที่บล็อกได้จริง ไม่ใช่ข้อตกลง**
ข้อตกลง**จางลงทุกชั้นที่เปิด session ต่อ** · ด่านไม่จาง เพราะมันไม่ได้อยู่ในบริบทของใคร

**② วัฒนธรรมรายงานสิ่งที่ตัวเองทำพัง**
วันเดียวมี 3 งวดที่ผลลัพธ์คือ *"บั๊กที่สั่งให้แก้ไม่มีจริง"* · *"เทสต์ที่ผมเขียนไม่ได้ตรวจอะไรเลย"* · *"สคริปต์ผมไปแตะข้อมูลลูกค้าจริง"*
> **ไม่มีงวดไหนทำให้ตัวเลขงานดูดีขึ้น — แต่มันกันงานผิดทิศ 3 ใบไม่ให้ถูก merge**

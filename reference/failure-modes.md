## ① ผลบวกลวงจากเครื่องมือวัด — **แพงที่สุด**

**ของจริง:** มีคนรายงานว่า *"ปิดกล่องแล้วทั้งหน้าค้าง ทำซ้ำได้ 100%"*
coordinator เชื่อ แล้วเปิดงานให้คนไปแก้ → **ไปวัดจริงแล้วไม่มีบั๊กนี้เลย**

**สาเหตุ:** เบราว์เซอร์ที่ใช้ตรวจถูกซ่อนอยู่ ⇒ หยุดเล่นแอนิเมชัน ⇒ กล่องปิดไม่จบ ⇒ **อาการเหมือนบั๊กจริงเป๊ะ**

**ราคา:** work order ทั้งใบ

🔑 **สิ่งที่ปิดประเด็นได้คือ *เคสควบคุม*** — เอาเคสที่**เกิดบั๊กนี้ไม่ได้โดยนิยาม** ไปวัดในสภาพเดียวกัน
ถ้าเคสควบคุมก็พัง ⇒ **เครื่องมือพัง ไม่ใช่โค้ดพัง**

⚠️ **และหลักฐานที่ *ดูเหมือน* ปิดประเด็นได้ อาจตกไปทั้งข้อ ถ้ามันวัดด้วยวิธีเดียวกัน**

## ② ความล้มลูกโซ่ทำให้ 1 บั๊กดูเหมือน 4

**ของจริง:** สคริปต์ทดสอบรายงาน *"7 ผ่าน / 4 ล้ม"*
ที่จริง **ข้อแรกพังเพราะรูปแบบข้อมูลผิด** แล้วอีก 3 ข้อล้มตามเพราะไม่มีข้อมูลให้ทำงานด้วย

> **ถ้าไม่ยิงตรวจซ้ำ จะสรุปว่า "ระบบสิทธิ์พัง" แล้วไปแก้ของที่ไม่ได้พังเลย**

✅ **สคริปต์ที่ทำเป็นลำดับขั้น ต้องแยกเสียง "ล้มเพราะตัวเอง" กับ "ล้มตามข้อก่อนหน้า"**

## ③ ตัวนับที่ไม่ตรวจสภาพตั้งต้น

**ของจริง:** วัดว่า "กดปุ่มแล้วกล่องเตือนขึ้นไหม" → ได้ว่าขึ้น → เกือบสรุปว่าปิดรูครบแล้ว
**ที่จริงกล่องนั้นค้างเปิดมาจากขั้นตอนก่อนหน้า**

🔴 **ผลลวงชนิดนี้อันตรายกว่าชนิดแรก** — ชนิดแรกทำให้ไป**หา**บั๊กที่ไม่มี · ชนิดนี้ทำให้**หยุดหา**รูที่ยังเปิดอยู่

✅ **ทุกตัวนับที่วัด "มีอะไรโผล่ขึ้นมาไหม" ต้องบันทึกด้วยว่า "ก่อนหน้านั้นมันโผล่อยู่แล้วหรือเปล่า"**

## ④ กระดานงานค้างที่ไม่เคยถูกตรวจซ้ำ

**ของจริง:** กวาดคำขอเก่าแล้วพบว่า **2 ใน 5 หมดอายุไปแล้ว**
- *"ฟังก์ชันนี้พัง หน้าหลักใช้ไม่ได้"* (ค้าง 16 วัน) → **เรียกจริงแล้วปกติดี**
- *"ต้องล้างช่องว่างในชื่อ 18 รายการ"* → **0 รายการ แก้ไปแล้วระหว่างทาง**

> **บันทึกงานค้างที่ไม่เคยถูกตรวจซ้ำ จะสะสมของที่หายไปแล้ว — แล้วคนอ่านจะเริ่มเมินทั้งรายการ**

✅ **ทุกคำขอต้องแนบ 1 คำสั่งที่รันแล้วบอกได้ว่ายังค้างจริงไหม**

## ⑤ เทสต์ที่แดงมั่ว

**ของจริง:** ชุดเทสต์โตถึง 940 ตัว แล้วเริ่มแดง 2–9 ตัวแบบสุ่ม
รันไฟล์เดียวกันเดี่ยวๆ → **เขียวหมด**

**สาเหตุ:** รันขนานเต็มคอร์ ⇒ เทสต์ที่รอ UI หมดเวลาเพราะเครื่องแน่น **ไม่ใช่เพราะโค้ดผิด**

> 🔴 **เทสต์ที่แดงมั่วทำลายค่าของทั้งชุด** — คนจะเริ่ม "รันใหม่จนเขียว"
> **แล้ววันที่มันแดงเพราะของจริงพัง จะไม่มีใครเชื่อมัน**

✅ **และตอนเจอแดง ต้องเก็บ output ไว้ก่อนรันซ้ำเสมอ** — ไม่งั้นเหลือแค่ *"น่าจะ flaky"* ซึ่งพิสูจน์ไม่ได้ ซ่อมไม่ได้

## ⑥ 🔴 **ด่าน 4 แบบที่เขียว/แดงโดยไม่ได้ตรวจสิ่งที่มันอ้างว่าตรวจ**

ทั้ง 4 แบบนี้เกิดขึ้น **ในวันเดียวกัน** และทุกแบบผ่านสายตามาแล้วรอบหนึ่ง

### ⑥.1 ด่านที่เขียวเพราะ**ไม่เคยแตะบรรทัดที่มันตรวจ**

แก้บั๊กในฟังก์ชันที่มีหลายสาขา `return` แล้วเขียนด่านโดยหยิบข้อมูลจริงมาทดสอบ
**แต่ข้อมูลที่หยิบมาทุกใบ `return` ออกตั้งแต่สาขาแรก ไม่เคยเดินถึงบรรทัดที่แก้เลย**

```
ทดสอบกลายพันธุ์: ใส่ `and false` เข้าไปในสาขาที่แก้  →  ด่านยังเขียว
วัดยืนยัน: ข้อมูลที่เข้าเงื่อนไข 14 ใบ · ที่เดินถึงสาขานั้น 0 ใบ
```

⇒ **เลือกเคสทดสอบจาก "เดินผ่านโค้ดที่แก้ไหม" ไม่ใช่จาก "เกี่ยวข้องกับหัวข้อไหม"**

### ⑥.2 ด่านที่แดงเพราะไป**จับคอมเมนต์ที่ตัวเองเขียน**

ด่านค้นหาชื่อคอลัมน์เก่าในนิยามฟังก์ชันเพื่อยืนยันว่าแก้แล้ว —
**แต่คอมเมนต์ที่อธิบายบั๊กก็มีชื่อคอลัมน์เก่าอยู่** ⇒ แดงทั้งที่โค้ดถูก

⇒ **ตัดคอมเมนต์ออกก่อนค้นเสมอ** เมื่อค้นหาในซอร์สที่ตัวเองเพิ่งเขียนคำอธิบายลงไป

### ⑥.3 ด่านที่ฝัง**เลขที่คนนับเอง**

*"policy ฝั่งเขียนต้องเหลือ 8 ตัว"* — ของจริง 11 ⇒ ด่านแดงทั้งที่ migration ถูก

⇒ **ถ่ายภาพสภาพก่อนเริ่ม แล้วเทียบทีละรายการ** (`EXCEPT` สองทาง จับได้ทั้ง "หายไป" และ "โผล่มาใหม่")
**เลิกใส่เลขที่คนนับลงด่าน**

### ⑥.4 probe ที่วัดด้วยเครื่องมือที่**ข้ามสิ่งที่กำลังจะวัด**

ตรวจว่าปิดสิทธิ์สำเร็จไหม โดยยิงผ่าน API ผู้ดูแลระบบ ซึ่งรันด้วยสิทธิ์สูงสุด
⇒ **ข้ามด่านสิทธิ์ทั้งหมดโดยธรรมชาติ** ⇒ ได้ผลว่า "ยังเปิดอยู่" ทั้งที่ปิดสำเร็จแล้ว

⇒ **เครื่องมือฝั่งผู้ดูแลระบบใช้พิสูจน์เรื่องสิทธิ์ไม่ได้ ไม่ว่ากรณีใด** — ต้องยิงผ่านทางเดียวกับผู้ใช้จริง

## 🧪 ท่าที่ปิดทั้ง 4 แบบพร้อมกัน: **เคสควบคุมสองด้าน**

ด่านที่เชื่อได้ต้องมีทั้ง:

| | |
|---|---|
| **เคสลบ** | ของที่ควรถูกบล็อก → **ถูกบล็อกจริง** |
| **เคสบวก** | ของที่ควรผ่าน → **ผ่านจริง** |

ตัวอย่างที่ใช้ได้จริง — ตรวจว่าปิดช่องเขียนสำเร็จ โดยดู **รหัส error ที่ต่างกัน** ไม่ใช่ดูว่าสำเร็จหรือไม่:

```
                       ก่อนแก้              หลังแก้
คนนอก → ตารางเป้าหมาย   ผ่านด่าน ตายที่ FK   ถูกด่านปฏิเสธ   ✅
คนนอก → ตารางคุมเทียบ   ถูกด่านปฏิเสธ        ถูกด่านปฏิเสธ   ← probe ไม่ได้พังเอง
แอดมิน → ตารางเป้าหมาย  —                    ผ่านด่าน       ← ไม่ได้ปิดจนไม่มีใครทำงานได้
```

> 🔑 **ทั้งสามบรรทัดต้องเปลี่ยนไปคนละทาง** — ถ้าแถวแอดมินกลายเป็น "ถูกปฏิเสธ" ด้วย แปลว่าปิดแรงเกิน
> **ด่านที่มีแต่เคสลบ พิสูจน์ได้แค่ว่า "อะไรบางอย่างพัง" ไม่ได้พิสูจน์ว่าพังถูกจุด**

## 🧨 กับดักพิเศษ: การอ้างถึงของที่ถูก rollback

**ของจริง:** ทดสอบด้วยธุรกรรมที่ยกเลิกทิ้งทั้งหมด → สะอาดมาก ไม่เหลือร่องรอย
**แต่เลขที่ระบบออกให้ตอนทดสอบ ถูกคืนเข้ากอง แล้วข้อมูลจริงใบถัดไปหยิบไปใช้ภายในไม่กี่นาที**

⇒ รายงานที่เขียนว่า *"บิลทดสอบเลขที่ X"* **ชี้ไปที่ข้อมูลลูกค้าจริงในอีก 30 นาที**

> **ความสะอาดแบบ rollback ทำให้ตัวระบุที่ใช้อ้างถึงของทดสอบ ไม่ได้เป็นของเราอีกต่อไป**

✅ **ห้ามอ้างเลขที่ระบบสร้างให้ ในรายงานของงานที่จบด้วย rollback**

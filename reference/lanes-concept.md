## ปัญหาที่ LANES แก้

รัน Claude Code หลาย session พร้อมกันบนรีโปเดียว จะเจอ 4 อย่างนี้เสมอ:

1. **เขียนทับกัน** — สอง session แก้ไฟล์เดียวกัน คนที่ merge ทีหลังชนะเงียบๆ
2. **งานหาย** — session จบแล้วแต่ยังไม่ push · ไม่มีใครรู้จนกว่าจะมีคนไปไล่หา
3. **กติกาจาง** — session ที่ 3 ที่ถูก chip ต่อมา ไม่รู้กฎที่ session ที่ 1 เพิ่งเรียนรู้
4. **ตัวเลขที่เชื่อไม่ได้** — แต่ละ session รายงานตัวเลขที่วัดคนละวิธี แล้วเอามารวมกัน

> 🔑 **ข้อ 4 เป็นข้อที่แพงที่สุด และเป็นข้อที่ระบบส่วนใหญ่ไม่แก้**
> เพราะ 3 ข้อแรกพังแล้วเห็นทันที · ข้อ 4 พังแล้ว**ดูเหมือนทำงานได้ปกติ**

## L — Lanes (เขตไฟล์)

**แต่ละแผนกได้ path ของตัวเอง · แตะนอกเขต = CI ตีกลับ**

```
domains.frontend = ["src/components/frontend/", "src/pages/Home.tsx"]
coordinatorLocked = ["src/lib/", "src/config/"]
```

### ทำไมต้องเป็นด่านที่บล็อกจริง ไม่ใช่ข้อตกลง

**ข้อตกลงจางลงทุกชั้นที่ chip ต่อ** — session ที่ 1 อ่านกติกาครบ · session ที่ 3 ได้ยินมาจาก session ที่ 2
**ด่านไม่จาง** เพราะมันไม่ได้อยู่ในบริบทของใคร

### 🔴 สิ่งที่ Lanes กันไม่ได้

**semantic conflict** — สอง session แก้คนละไฟล์ แต่ตกลงกันคนละอย่างเรื่อง API, สคีมา, หรือกฎธุรกิจ
> เกิดจริง: สอง session แก้ **ข้อความเทมเพลตเดียวกัน** คนละชั้น (ไฟล์ default ในโค้ด กับแถวใน DB)
> **ไฟล์ไม่ชนกัน แต่ผลลัพธ์ขัดกัน**

⇒ **ต้องมีคนตัดสิน (coordinator) เสมอ — Lanes ไม่ได้แทนคน มันแค่ลดจำนวนเรื่องที่คนต้องตัดสิน**

### กติกายกไฟล์กลางรายไฟล์

ถ้าไฟล์ในเขตกลางมี**ผู้ใช้แผนกเดียว** ให้ยกเป็นของแผนกนั้นเลย (exact-file grant ชนะ prefix lock)
**พิสูจน์ก่อนยก:** `git grep -ln "<ชื่อไฟล์>" -- src` — ผู้ import ต้องอยู่แผนกเดียวทั้งหมด

> **ทุกไฟล์ที่ยกออกไป = งานที่ไม่ต้องรอ coordinator อีกต่อไป**
> **แก้คอขวดโดยไม่ลดความปลอดภัย**

## A — Auto-merge (ด่าน)

**commit สุดท้ายขึ้นต้น `done(<แผนก>-<งาน>):` → CI ตรวจ 5 ด่าน → merge เอง**

```
① มี done() commit
② ไม่แตะไฟล์นอกเขต
③ build เขียว
④ typecheck เขียว        ← หลาย CI ไม่ทำข้อนี้ ต้องเพิ่มเอง
⑤ tests เขียว
```

**ผลจริง: เวลารอ merge มัธยฐาน 1 นาที** — คนไม่ต้องมานั่งเฝ้า

### 🔴 กับดัก 2 ข้อที่เจอมาแล้ว

**① อย่าให้ robot ลบ branch หลัง merge**
เกิดจริง: งานที่ push ยังไม่เสร็จหายไป **3 ครั้งในวันเดียว**

**② งานที่ตีกลับต้อง "ดัง" ไม่ใช่เงียบ**
เกิดจริง: งานเสร็จตั้งแต่เช้า แตะไฟล์กลางเลยตีกลับ **แล้วไม่มีใครรู้จนกวาดตอนเย็น**
⇒ `board-sweep.sh` ต้องมีหมวด *"งานที่รอ coordinator"* แยกออกมา

## N — Notes (ความจำที่อยู่นอกบทสนทนา)

**3 ไฟล์ที่ต้องมี**

| ไฟล์ | เก็บอะไร | ทำไม |
|---|---|---|
| `CLAUDE.md` | กฎที่ห้ามพลาด | โหลดอัตโนมัติทุก session |
| `docs/team/lessons/<หมวด>.md` | บทเรียนสะสม | **อ่านเฉพาะหมวดที่เกี่ยว** |
| `docs/team/decisions.md` | เจ้าของโปรเจกต์ตัดสินอะไรไปแล้ว | **ต่อท้ายอย่างเดียว ห้ามแก้ของเก่า** |

### ทำไม `decisions.md` สำคัญกว่าที่คิด

เกิดจริง: เจ้าของตัดสินใจ **~15 เรื่องในวันเดียว** และมันอยู่ใน**บริบทของ coordinator ที่เดียว**
⇒ ถ้า session นั้นหาย **ทีมไม่มีทางรู้ว่าอะไรเคาะไปแล้ว** → ไปถามซ้ำ หรือแย่กว่า คือ**เดาเอง**

**และมันเป็นต้นเหตุของ "ข้อความสวนกัน"** — เพราะสถานะการตัดสินใจอยู่ในข้อความ ไม่ใช่ในที่ที่อ่านได้ตลอดเวลา

### 🔴 กับดักใหญ่: ไฟล์กติกาบวมจนย้อนมาทำร้ายตัวเอง

เกิดจริง: ไฟล์กติกาโต **6.3 เท่าใน 8 วัน** ⇒ ทุก session ต้องอ่าน **~17,500 tokens ก่อนเริ่มงาน**

> **เราเขียนกติกาเพิ่มทุกครั้งที่พลาด เพื่อไม่ให้พลาดซ้ำ**
> **แต่ยิ่งเขียน โอกาสที่กติกาข้อใดข้อหนึ่งถูกมองข้ามก็ยิ่งสูง**

⇒ วิธีแก้อยู่ใน [`context-hygiene.md`](context-hygiene.md)

## E — Evidence (ห้ามเชื่อสิ่งที่ยังไม่ได้วัด)

**เสานี้ไม่มีไฟล์คอนฟิก มีแต่วินัย — และเป็นเสาที่ทำให้ 4 เสาที่เหลือเชื่อถือได้**

### 3 กฎแกน

**① ด่านต้องพิสูจน์ว่าแดงได้จริง — และเขียวได้จริง**
ด่านที่ไม่เคยเห็นตัวเองแดง = ไม่ใช่ด่าน
**ด่านที่แดงเสมอก็ไม่ใช่ด่าน** — เกิดจริง: ด่านใน migration ตัวหนึ่งฟ้องผิดทุกครั้ง เพราะเขียน regex โดยเดาว่าฐานข้อมูลจะคืนค่ามาเป็นตัวพิมพ์เล็ก

**② เครื่องมือวัดต้องถูกวัดก่อน**
เกิดจริง 3 หน้าตาในวันเดียว:
- สคริปต์นับแถวบนหน้าจอ **นับเกิน** เพราะ layout เปลี่ยนใต้มันแล้วไม่มีใครสอบเทียบใหม่
- เทสต์ที่อ่านซอร์สโค้ด **เขียวทั้งที่ถอดโค้ดจริงออก** เพราะบรรทัด `import` ก็มีชื่อฟังก์ชันนั้น
- ตัวพิสูจน์ "กำลังดูโค้ดตัวเอง" **บอกว่าโค้ดไม่ขึ้น** เพราะ build tool แปลงไวยากรณ์ทิ้งไปแล้ว

> 🔑 **แก่นร่วม: เราเชื่อสิ่งที่ *อ่านได้* แทนสิ่งที่ *รันอยู่***
> **ท่าที่ปิดทั้งสามพร้อมกัน: ถอด fix ออกแล้วดูว่ามันพังจริงไหม**
> ถ้าถอดแล้วยังเขียว = **สิ่งที่คุณตรวจ ไม่ใช่สิ่งที่ทำให้มันทำงาน**

**③ ตัวเลขต้องมีหน่วย · บวกได้ลงตัว · และบอกว่าใครวัด**
เลขที่กระทบกันไม่ลง = มีอันหนึ่งผิด **ห้ามส่งต่อ**
เทียบก่อน/หลัง **ต้องรันคิวรีตัวเดิม** ไม่ใช่คิวรีที่ตอบคำถามเดียวกัน

### 🔑 วัฒนธรรมที่ทำให้ E ทำงานจริง

**session ต้องรายงานสิ่งที่ตัวเองทำพังได้ โดยไม่ถูกลงโทษ**

เกิดจริงในวันเดียว — 3 งวดที่ผลลัพธ์คือ:
- *"บั๊กที่สั่งให้ไปแก้ ไม่มีอยู่จริง — เครื่องมือวัดพัง"*
- *"เทสต์ที่ผมเพิ่งเขียน ไม่ได้ตรวจอะไรเลย"*
- *"สคริปต์ QA ของผมไปแตะข้อมูลลูกค้าจริง"*

> **สามงวดนั้นไม่มีงวดไหนทำให้ตัวเลขงานดูดีขึ้นเลย**
> **แต่มันกันงานผิดทิศ 3 ใบไม่ให้ถูก merge**

⇒ **ถ้าทีมทำ E ไม่ได้ ตัวเลขทุกตัวที่ระบบรายงานจะเชื่อไม่ได้ — และไม่มีใครรู้ว่ามันเชื่อไม่ได้**

## S — Scope (เลือกหน่วยงานให้ถูก)

> ## **งานที่ไม่จบด้วย commit → subagent · งานที่จบด้วย commit → session**

| | subagent | session |
|---|---|---|
| บริบท | สะอาด คืนแค่สรุป 1,000–2,000 tokens | หน้าต่างแยกทั้งอัน |
| เถียงกลับได้ | ❌ | ✅ |

**subagent:** วัด · กวาด grep · ยิงคิวรีนับ · อ่าน log · ตรวจว่าคำขอเก่ายังค้างไหม
**session:** งานที่ต้องตัดสินใจระหว่างทาง

### เพดานจำนวน

**3–5 session พร้อมกัน** — เกิน 8 **คอขวดจะกลายเป็นคนรีวิว ไม่ใช่โมเดล**
เกิดจริง: แตะ 21 branch แล้ว coordinator กลายเป็นคอขวด · งานเสร็จแล้วค้างโดยไม่มีใครรู้

## ทำไมเสาใดเสาหนึ่งหายแล้วพัง

| ขาดเสา | อาการ |
|---|---|
| ขาด **L** | เขียนทับกันเงียบๆ · เจอตอน merge หรือตอนของพังบน production |
| ขาด **A** | คนกลายเป็นคอขวดตั้งแต่วันแรก · งานเสร็จแล้วนอนรอ |
| ขาด **N** | กติกาจางลงทุกชั้นที่ chip ต่อ · ถามเรื่องเดิมซ้ำ · ตัดสินใจซ้ำ/ขัดกัน |
| ขาด **E** | 🔴 **ระบบดูเหมือนทำงานได้ แต่ตัวเลขที่รายงานเชื่อไม่ได้** — อาการที่แพงที่สุดเพราะมองไม่เห็น |
| ขาด **S** | จ่าย token แพงเกินจำเป็น · เปิด session เยอะจนคนรีวิวไม่ทัน |

> 🔑 **L กับ A ทำให้ทำงานขนานได้**
> **N กับ E ทำให้ผลลัพธ์เชื่อถือได้**
> **S ทำให้มันคุ้ม**
>
> **ทีมส่วนใหญ่ทำแค่ L กับ A แล้วสงสัยว่าทำไมยิ่งขนานยิ่งพลาด**
